# kangaroo_ring_controller: ring-attractor joint control on PAL Kangaroo (ROS 2)

The TIAGo spiking ring-attractor joint controller (`src/tiago_ring_controller/`), ported to the arms of PAL's Kangaroo
in MuJoCo on ROS 2 Humble. The ring decides a joint velocity every 50 ms; the arm executes it as a short
receding-horizon `JointTrajectory`, as on TIAGo. The ring core is reused unchanged from the TIAGo package.

- Design (control loop, modules, data, choices): `docs/kangaroo/DESIGN.md`
- Experiments and results: `docs/kangaroo/EXPERIMENTS.md`
- Library modules: `kangaroo_ring_controller/README.md`

**Status:** all 8 arm joints calibrated (measured range, settle guard, batch refit). 320 seeded reaches on the
simulated robot: every joint-direction median relative error < 0.5 (0.07-0.31), 95 % of sampled goals reached the
right way.

## Run
Everything runs inside the `docker/ros2_kangaroo` container, from any directory (commands are from `/work`):

```bash
docker/ros2_kangaroo/run.bash
ros2 launch /opt/kangaroo_sim.launch.py &      # simulation + left/right arm controllers
```

### Drive a joint from the browser
```bash
python3 src/kangaroo_ring_controller/scripts/ring_gui.py   # then open http://localhost:8765/ on the host
```
Pick the arm and joint, drag the **goal slider** (bounded to the joint's ring range) and release: the ring drives
the joint from where it is toward the goal; releasing again mid-reach replaces the goal. **Reset** returns the arm
to the joint's start pose, **Stop** ends the reach. A ring takes 22-30 s to build, so the GUI builds the next one
while idle ("ready"). Each reach uses the joint's newest calibration.

### Command-line tools (`scripts/`)
```bash
S=src/kangaroo_ring_controller/scripts
python3 $S/arm_velocity.py left 2 -0.3 1.5        # arm_left_3_joint at -0.3 rad/s for 1.5 s
python3 $S/ring_reach.py left 0 -0.8 [--seed 12345] [--calibration <calibration.json> --from-home | --limits <limits.json>]
python3 $S/joint_limits.py right 1                # reachable range -> results/joint_limits/
python3 $S/calibrate.py right 1 --balanced --start-joint 0.161 --limits <limits.json>   # 100 trials -> results/calibration/
python3 $S/refit_calibration.py <calibration.json> ... [--last 50]   # batch refit of the decoder -> results/calibration/
python3 $S/evaluate.py <left|right> [--name eval] [--resume DIR] [--dry-run]   # 160 seeded reaches per arm
python3 $S/plot_results.py [--evaluation DIR ...] [--trials GLOB] [--calibrations GLOB] [--refit FILE]   # figures
python3 $S/experiments/velocity_tracking.py       # commanded vs measured joint velocity
python3 $S/experiments/settle_replay.py <trial.json> ...   # replay saved spikes: when does the decoder settle
```
- Joints are `0-3`, meaning `arm_<side>_1..4_joint`. NEST's kernel is global, so one ring per process: to drive both
  arms at once, run one process per arm.
- Without a calibration the decoder is TIAGo's uncalibrated default (k = ±1e-4): the joint moves the right way but
  only a few percent of the distance.
- To recalibrate a joint: `joint_limits.py`, then `calibrate.py`, then `refit_calibration.py` on its output; the
  newest `calibration.json` per joint is what reaches and the GUI use. Add it to git with `git add -f`.

## Results
Every run writes a new `results/<kind>/<name>_<time>/` directory; nothing is overwritten. Only the 8 calibrations
in use (`results/calibration/`) are in the repo; trials, evaluations and figures are regenerated by the tools above.

## Tests
```bash
python3 -m unittest discover -s src/kangaroo_ring_controller/test -v                  # all, about 17 min
python3 -m unittest discover -s src/kangaroo_ring_controller/test -v -p test_gui.py   # one file
```
76 behaviour tests with independent oracles, no mocking of the ring or the plant. Tests of `arm`, `ring`,
`calibration`, `limits` and `gui` need the simulation running; the rest (evaluation, plots, joint setup, refit,
settle, warm spare, CLIs) do not.
