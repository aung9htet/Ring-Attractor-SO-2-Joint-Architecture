# Kangaroo ring controller: design overview

How the TIAGo spiking ring-attractor controller was ported to PAL Kangaroo (ROS 2 Humble, MuJoCo), how the pieces
fit, and which choices a developer must know before changing them. Results: `EXPERIMENTS.md`.

## The control loop (one reach of one joint)
```
q_start, q_goal ──map──> ring indices ──> NEST ring (r1 = start, r2 = goal)
                                               │ every 50 ms tick
                                               ▼
              signed = right − left gain-modulation spikes
              d = a·d + (1−a)·signed,  a = exp(−dt/τ),  then delayed by `delay` ticks
              v = k_pos·d (d ≥ 0)  or  k_neg·(−d) (d < 0)          [rad/s]
                                               │
                                               ▼
        Kangaroo arm: v → short receding-horizon JointTrajectory → PAL arm_<side>_controller
```
- **Map:** q ∈ [joint_min, joint_max] → ring index, linear, not wrapped.
- **Open loop in q:** the ring sees the robot only at trial start; the joint state is read for the record, not fed
  back into the ring.
- **Stop:** `drive_settled` after 10 ticks of |delayed d| < 5, counted only once |delayed d| has first reached 5
  (the settle guard); otherwise `max_steps`.
- **Velocity control** is not a native velocity interface: PAL's controllers take position trajectories, so each
  tick's v is integrated into a short trajectory (the same path TIAGo used).

## Where the code lives
- `src/tiago_ring_controller/`: the TIAGo package (ROS 1), a SHA-256-verified recovery. **Not modified.** It holds
  the ring core: NEST ring (`single_ring.SingleRingModel`), decoder core, calibration fit.
- `src/kangaroo_ring_controller/`: the Kangaroo package, same shape as TIAGo's (library / scripts / test / results).
  `ring_core.py` is the only module that knows where the TIAGo core is: it puts it on `sys.path` and gives absolute
  config paths, so everything runs from any working directory.
- `docker/ros2_kangaroo/`: the image and the simulation launch.

Rejected: extracting the ring core into its own package. It would break the TIAGo recovery manifest, catkin build
and launcher; worth revisiting if a third robot arrives.

## Modules (`kangaroo_ring_controller/`)
| Module | Responsibility |
|---|---|
| `arm.py` | Velocity control of one joint; owns the ROS node and the arm side (sleep, hold, reset to a pose) |
| `ring.py` | `RingDrive` (ring + decoder for one joint setup) and `run_trial` (one reach) |
| `settle.py` | `GuardedDriveCore`: TIAGo's decoder core with the settle guard |
| `ring_core.py` | Path bridge to the TIAGo ring core |
| `joint_setup.py` | `JointSetup`: everything a trial runs under; save/load `calibration.json`; `newest_setup` |
| `calibration.py` | TIAGo's calibration loop (100 trials, fit every 3, β = 0.5) |
| `refit.py` | Batch refit: TIAGo's fit once over the last 50 trials |
| `limits.py` | Measured reachable range of a joint (drive to each stop) |
| `evaluation.py` | Multi-seed protocol, resume, statistics, verdict (pure, no ROS) |
| `plots.py` | Figures from saved JSON (pure) |
| `gui.py`, `gui_page.py`, `warm_spare.py` | Browser GUI: drag a goal slider, the ring drives the joint live |
| `__init__.py` | `new_run_dir`, `save_trial` (one `trial.json` writer) |

## Data
Every run writes a new timestamped directory under `src/kangaroo_ring_controller/results/` (never overwritten).
Only the calibrations in use are committed; the rest is regenerated by the scripts.
- `calibration/<side>_j<n>_seed<s>_<time>/calibration.json`: `side`, `joint`, `profile`, `joint_limits` [rad],
  `start_pose` (4 joint angles, rad), `decoder_gain_positive` / `_negative` [rad/s per spike], `decoder_tau` [s],
  `decoder_delay_steps`, `seed`; a calibration run adds its `trials`, a refit adds `refit_of`, `refit_trials`.
  The controller loads the newest file per joint (`joint_setup.newest_setup`, by timestamp).
- `trial.json` (one reach): per-tick `signed_spike`, `signed_drive`, `decoded_velocity`, `joint_position`; `q_start`,
  `q_goal`, `q_final` [rad], `stop_reason`, `seed`, decoder values, `nest_version`.

## Choices to know before changing things
| Choice | Why | Rejected |
|---|---|---|
| Port TIAGo's code paths, not re-implement them | Results must be comparable with the paper | A cleaner new controller |
| Settle guard | TIAGo's rule stopped slow / delayed decoders before their drive arrived | Keep TIAGo's rule (3 of 12 reaches never moved) |
| Batch refit after calibration | The online 3-trial fit was the main error source; the plant moves 97-100 % of the command | Retune PAL's gains |
| Measured joint range | Right j1 cannot reach 27 % of its URDF range | URDF limits |
| Balanced goals, mid-range start | Otherwise one gain is barely identified and can come out wrong-signed | Goals uniform over the range from home |
| One process per arm | NEST and rclpy run in the main thread; two arms in parallel need two processes | Threads |
| Evaluation on the simulated robot only | The headline must not rest on a plant model | Offline ring-only or hybrid evaluation |

## Testing
`src/kangaroo_ring_controller/test/`, standard `unittest`. Behaviour tests with independent oracles (hand-computed
values, invariants); the ring and the plant are not mocked. Pure modules (evaluation, plots, joint setup, refit,
settle, warm spare) run without the simulation; arm, ring, calibration and limits tests need it running. Full suite:
about 17 min, see the package README for the command.

Code comments cite decision numbers (D…, F…, Q…) from the author's working log, which is not in the repo; the
reason behind each is summarised above.
